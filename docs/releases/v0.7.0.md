# v0.7.0 — All-In-One Free SEO Tool

**Release date:** 2026-10-22
**Diff:** [v0.6.3 → v0.7.0](https://github.com/akshat-mechlin/All-In-One-Free-SEO-Tool/compare/v0.6.3...v0.7.0)

A security and reliability release. One reported issue fixed (#43,
Google Business Profile posting), and the results of a full audit of the
codebase: thirty findings, most of them the same kind of fault this
project keeps finding — something that looked like it worked, and didn't.

**If you run this with a password or with team accounts, update.** Data
exports could be downloaded without signing in.

---

## 🔒 Security

### Data exports skipped the login

The request gate skipped "any path with a dot in it", meant for images and
scripts. That also covered every export — `/clients/export.csv` (names,
emails, phones, addresses), keywords, tasks, backlinks, audits, reports,
the disavow file and the plan PDF. With `APP_PASSWORD` set, all of them
downloaded with no login. Now only static-file extensions skip the gate,
and a test pins every export as protected.

### Team roles are enforced on the server

"Client viewer: read-only", "Manager: can't change integration keys" and
"Member: only assigned clients" were enforced by which pages rendered —
not by the server actions behind them, which anyone signed in could call
with any arguments. Every server action (424 of them) now starts with a
role check, and the test suite fails if a new one doesn't:

- **viewers** can read but not change anything;
- **settings, keys, integrations, the team and deleting clients** are
  owner-only, and the Settings screens show non-owners a short notice
  instead of the configuration;
- **members** can only act on clients they're assigned to;
- exports only include clients you can see.

Backup, restore, update and restart now require the **owner** when
accounts are on. Before, any signed-in account — a client viewer
included — could download or replace the whole database.

### Smaller fixes

- **Sign-in attempts are limited** (failed attempts only, so a team
  signing in can't lock itself out).
- **Client-portal AI chat** is rate-limited per link and overall, and its
  history is capped. Anyone with a forwarded portal link could run up
  your AI bill.
- **Public grader:** rate limits no longer trust a caller-supplied
  `X-Forwarded-For`, and there is an overall hourly ceiling.
- With no password set, a request whose `Host` named another machine was
  still treated as local by the admin endpoints. It isn't any more.
- The shared-password cookie is `Secure` behind an HTTPS reverse proxy.
- The public health check no longer tells remote callers your install
  path and process ID.

## 📍 Google Business Profile posting works (#43)

Posting to Business Profile failed every time, with Google's HTML 404 page
stored as the error. The schedule's "location" was free text, so a
business name became part of the URL: `POST /v4/Mono Web/localPosts`.

- Posts go to **the listing chosen for the client** (GBP → client →
  Reviews → "Which listing"). A per-schedule override still works if it's
  a real `accounts/…/locations/…` name; anything else is refused when you
  save.
- The listing picker no longer rejects every listing (Google's two APIs
  name locations differently).
- The call-to-action button links to the client's website — Google
  rejects a button with no link.
- Errors read as sentences, never HTML. An expired Google sign-in says so
  and explains the 7-day "Testing" consent-screen limit.
- Failed posts have **Retry publish**; approved ones **Publish now**.
  Auto-publish posts go out right after they're written, not up to a day
  later.

Thanks to **@Galbir**, whose report and pull request (#44) mapped every
step of the failure.

## ⚙️ Automation that actually runs

- **Weekly jobs ran only on Mondays.** The AI audit and SERP-feature
  snapshot ran only if the daily pass happened to start on a Monday (UTC)
  — never, on a desktop install that's closed on Mondays. They now run
  whenever a week has passed.
- **Rank tracking** checked 30 keywords a *week*, across every client, and
  counted blocked checks as successes. It now checks a rotating share
  every day (default 30/day), so every keyword is re-checked at least
  weekly, and a blocked sweep is reported as an error.
- **Client #31 was never checked.** Several daily jobs (robots.txt watch,
  sitemap health, traffic-drop alerts, AI suggestions, weekly AI audit)
  only ever looked at the first 8–30 clients. They now take turns through
  all of them.
- **A failing scheduled report retried every few minutes, forever** —
  rebuilding the PDF and logging an error each time. It now backs off and
  gives up for that period after six attempts.
- The background scheduler backs off failed jobs instead of retrying every
  minute, and passes can't overlap.
- The page monitor said "hourly" and ran daily, and hid its own errors.
  It's daily, labelled daily, and its failures show in Automations.
- **Time zone for scheduled reports** — Settings → General. "9 AM" used to
  mean 9 AM server time, which is UTC on Docker. "Last day of the month"
  is now an option (it was capped at the 28th).

## 🧾 Tasks and invoices

- Un-ticking and re-ticking a recurring task created a **duplicate** next
  copy, and the copy lost its assignee, estimate and tool link. Fixed;
  bulk "mark done" now behaves like a single one.
- **Invoice numbers could repeat**: the next number was "count + 1", so
  deleting an invoice reissued an existing number. Numbers now continue
  from the highest ever issued, restart each year, and a duplicate is
  refused. Invalid line items are reported instead of silently dropped.

## ⚠️ Upgrading

- **No database migrations.** Your data is untouched.
- **Updates now rebuild.** Before this release, updating (the launcher's
  Update button or Settings → Update) pulled the new code but kept serving
  the old production build until `.next` was deleted. From this version,
  the first start after an update notices and rebuilds once (1–2 minutes)
  — including the start right after this update, because the launchers
  run the start script from the new code. Restart the app after updating.
- `src/middleware.ts` is now `src/proxy.ts` (Next 16's name). If you
  update by extracting the zip over your old folder, the old file is
  removed automatically on start.
- **Team accounts:** non-owners lose access to Settings and admin actions,
  as the role descriptions always said. Give someone the owner role if
  they need them.
- The WordPress plugin is unchanged at **0.6.1**.

### Known limitations

- Members are limited to their clients wherever an action receives a
  client id. A handful of actions receive only an item id (a task, an
  invoice); those are role-checked but don't yet look up the item's client.
- API keys and MCP tokens are workspace-wide (only the owner can create
  them).
- A Turbopack build warning about file tracing remains; it only affects
  the size of the optional standalone package, not the app.
