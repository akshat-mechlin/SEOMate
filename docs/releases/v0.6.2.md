# v0.6.2 — All-In-One Free SEO Tool

**Release date:** 2026-10-19
**Diff:** [v0.6.1 → v0.6.2](https://github.com/akshat-mechlin/All-In-One-Free-SEO-Tool/compare/v0.6.1...v0.6.2)

Two issues reported since v0.6.1, both fixed. Both were about the same
thing from different directions: being told to open a terminal, or being
told to go and look something up, when the software could have just done
it.

---

## "The headless browser isn't installed yet. Run `npx playwright install chromium`" (#37)

The reporter installed by double-clicking the launcher — which exists
precisely so nobody needs a terminal — and then, mid-task, was told to
open one.

Three faults in a single line of the installer, which together made this
invisible:

```cmd
call !PM! exec playwright install chromium 2>nul
```

1. The guard above it tested
   `node_modules\playwright\...\browser-chromium`. Playwright does not
   put browsers there — it uses `%LOCALAPPDATA%\ms-playwright` — so the
   check never matched anything.
2. `2>nul` discarded the error, so a failed download printed nothing.
3. Nothing read the exit code, so setup carried on and reported
   **"First-run setup complete."**

Now: the download is checked against the path Playwright actually uses,
failures are printed with the likely cause, and setup says plainly that
Chromium is missing while confirming everything else installed.

**And there is a button.** The launcher has **Install headless browser**
next to Back up now, so the fix matches the way the software was
installed. The error message points at that button first and mentions
the terminal command second, for people who prefer it.

Only rank checks, SERP scraping and screenshots need Chromium. Audits
and content tools never did.

## A Server Components error with a digest and no message (#36)

v0.6.1 started recording the real, unredacted server error against the
digest Next shows the browser. That worked — this report arrived with
`Digest 2102528023`, the app version, commit, OS, Node and browser all
filled in, where the previous one had none of it.

But it still had no message, because the error page said *"find this in
Settings → Errors for the real message"* and the reporter had no reason
to know that screen existed.

The page now looks it up itself. When an error has a digest, it resolves
it against this install's own error log and shows the actual message and
the first frames of the stack — on the error screen, and in the
pre-filled issue. Same machine, same database, two halves of the same
error; there was never a good reason to make a person carry a number
between them.

If the row has gone — the server restarted, or retention aged it out —
the report says so rather than implying nothing was recorded.
